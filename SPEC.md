# Canon Format Specification

**Document Status:** Living Standard  
**Authority:** Definitively governs Canon Clerk parser, screener, and auditor implementations.

---

## 1. Overview & Design Philosophy

Canon Clerk codifies and automates architectural guidelines, repository tenets, and review policies through **canons**—natural language rule definitions stored directly alongside code.

The specification is anchored on three core design principles:

1. **Zero Barrier to Entry:** Authoring a project rule should require virtually zero ceremony. A single sentence in a plain Markdown file is a valid, enforceable canon.
2. **Progressive Disclosure:** Advanced optimization features (such as deterministic Stage 0 path filtering, custom inspection scopes, or structured evaluation rubrics) are strictly opt-in.
3. **Clarity of Review Action:** The engine cleanly distinguishes between human action items (blocking issues the contributor must fix) and automated AI synthesis (non-blocking enhancements generated by the Clerk).

---

## 2. File Discovery & Scoping

Canons reside in `.canons/` directories within the target repository.

### 2.1 Repository-Wide Canons
By default, Canon Clerk discovers all Markdown files matching:
```text
**/.canons/**/*.md
```
Canons located at the repository root's `.canons/` directory are **global**—they are evaluated against the entire repository, subject only to their own `paths:` configuration or screener stage decisions.

### 2.2 Scoped Canons (Subdirectories & Monorepos)
Canons may also reside within subdirectory `.canons/` folders, such as in a monorepo package:
```text
packages/ui/.canons/button-accessibility.md
services/auth/.canons/token-revocation.md
```
**Scoping Rule:** A canon residing in `<scope>/.canons/` automatically inherits an implicit path boundary of `<scope>/**`. If a pull request modifies zero files under `<scope>/`, the canon is deterministically discarded at Stage 0 without token consumption.

---

## 3. Progressive Disclosure (The 4 Tiers)

To balance rapid onboarding with fine-grained performance control, canons support four progressive tiers:

### Tier 1: Minimal Viable Canon (Zero Friction)
A Tier 1 canon is a plain Markdown file containing a natural language invariant. It requires **no YAML frontmatter**, **no headers**, and **no metadata boilerplate**:

```markdown
PRs that introduce new user-facing features must have accompanying documentation in `docs/`.
```

### Tier 2: Keyword Directives
Authors can enable a canon evaluator to supply actionable _Guidance_ or automated _Supplement_ synthesis instructions directly within the prose using bold keyword markers:

```markdown
PRs introducing user-facing features must update documentation. **Guidance:** Suggest which section under `docs/` should be updated.
```

```markdown
PRs modifying user-facing visual component behavior must include a manual Test Script. **Supplement:** If feasible, synthesize a candidate manual Test Script from the PR diff and description conforming to industry standards.
```

### Tier 3: Cost-Optimized Canon
A Tier 3 canon adds minimal YAML frontmatter purely to enable **Stage 0 deterministic path filtering** or specify targeted context scopes. This avoids invoking language models when the PR touches unrelated files:

```markdown
---
paths:
  - "src/components/**"
  - "public/**"
---

PRs modifying user-facing visual component behavior must include a manual Test Script. **Supplement:** If feasible, synthesize a candidate manual Test Script from the PR diff and description conforming to industry standards.
```

### Tier 4: Structured / Multi-Section Canon
For complex invariants requiring detailed rubrics, rationale, or extensive multi-step templates, authors may organize the document into explicit Markdown sections:

```markdown
---
title: Manual Test Script Required for UI Changes
paths:
  - "src/ui/**"
  - "frontend/**"
inspect:
  - pr_body
  - diff
---

## Rule
Any pull request modifying user-facing UI components must include a numbered `### Manual Test Script` in the PR description.

## Rationale
Manual verification instructions are required for the code reviewer to perform to prevent regressions in visual flow and interactive state transitions that automated unit tests may miss.

## Evaluation Criteria
- **Inapplicable**: Pure refactors, internal types, or non-visual utility changes with zero visual/behavioral impact.
- **Pass**: Description contains clear, reproducible, manual verification steps.
- **Fail**: UI components changed, but no manual test steps are present, or steps are ambiguous.

## Supplement
- **Warn**: Analyze the modified UI components and synthesize a candidate manual test script conforming to industry standard Test Script guidelines.
```

## 4. Metadata Schema & Fallback Hierarchies

When metadata fields are omitted, Canon Clerk derives them automatically using deterministic fallback rules.

### 4.1 Field Definitions

| Field | Type | Required? | Default / Resolution Order | Description |
| :--- | :--- | :--- | :--- | :--- |
| **`id`** | `string` | No | 1. Frontmatter `id:`<br>2. Relative file stem / slug | Unique machine identifier used in Check Runs, CLI output, and state tracking. |
| **`title`** | `string` | No | 1. Frontmatter `title:`<br>2. First `# Heading` in body<br>3. `id` value | Human-readable title displayed in check run summaries and reports. |
| **`paths`** | `string[]` | No | 1. Frontmatter `paths:`<br>2. `["**/*"]` (all files) | **Stage 0 filter.** Glob patterns evaluated against PR file changes. |
| **`inspect`** | `string[]` | No | 1. Frontmatter `inspect:`<br>2. `["diff", "pr_body"]` | **Stage 2 scope.** Context elements passed to the auditor (`diff`, `pr_body`, `commit_messages`). |

### 4.2 Derivation Rules

1. **`id` Derivation:**
   * If `id` is specified in frontmatter, normalize to lower kebab-case.
   * If omitted, derive from the file's path relative to its enclosing `.canons/` directory, omitting the `.md` extension.
   * *Example:* `.canons/manual-test-plan-required.md` $\rightarrow$ `id: manual-test-plan-required`.
   * *Example:* `.canons/auth/session-expiration.md` $\rightarrow$ `id: auth-session-expiration`.

2. **`title` Derivation:**
   * If `title` is specified in frontmatter, use as-is.
   * Otherwise, search the Markdown body for the first top-level or secondary heading (`# Title` or `## Title`).
   * If no heading exists, convert the file slug into title case:
     * *Example:* `no-new-features-without-documentation.md` $\rightarrow$ `"No New Features Without Documentation"`.
     * Strips leading numeric prefixes if present (e.g. `canon-0001-ui-test-plan` $\rightarrow$ `"Ui Test Plan"`).

3. **`paths` Derivation:**
   * If omitted, defaults to matching all files: `["**/*"]`.
   * If scoped inside `<scope>/.canons/`, patterns are automatically prefixed with `<scope>/`.

4. **`inspect` Derivation:**
   * If omitted, defaults to `["diff", "pr_body"]`.
   * Available inspection tokens:
     * `diff`: The unified git diff of modified files.
     * `pr_body`: The pull request description / body.
     * `commit_messages`: The commit messages comprising the pull request.

## 5. Directive Semantics: `Guidance` vs. `Supplement`

Canon Clerk recognizes two, unambiguous, first-class directives for shaping agent-generated responses:

| Directive | Target Actor | CI Verdict | Meaning & Execution Contract |
| :--- | :--- | :--- | :--- |
| **None** (Default) | Contributor | **`fail`** (Blocking) | The pull request violates the canon. Fails immediately with rationale; no additional advice or generation is performed. |
| **`Guidance`** | Contributor | **`fail`** (Blocking) | **Human/AI instruction.** The Clerk instructs the contributor on what specific actions or edits *they* must take to unblock the PR (e.g., pointing to templates, docs, or required formats). |
| **`Supplement`** | Clerk AI | **`warn`** (Non-blocking)* | **Automated synthesis.** The Clerk fulfills the requirement on behalf of the author by synthesizing the missing material directly into the Check Run output (e.g., drafting a manual test plan). |

> **\*Graceful Fallback for `Supplement`:**  
> If a canon specifies a `Supplement` directive, but the Deep Auditor cannot reliably synthesize the material (e.g., the diff is too complex, ambiguous, or lacks necessary context), the Clerk **must gracefully fall back to a blocking `fail`**, stating that automated synthesis was infeasible and that manual author action is required.

### 5.1 Dual Syntax Support
Both directives can be specified using either inline annotations or formal Markdown H2 headers:

#### A. Inline Annotation Syntax
Best suited for Tier 1 and Tier 2 canons:
```markdown
PRs adding public API endpoints must document response codes in docs/api.md. Guidance: Direct the author to docs/api-template.md and list the undocumented status codes.
```

```markdown
PRs modifying UI components must include manual verification steps. Supplement: If feasible, synthesize a reproducible manual test plan from the diff.
```

Inline markers SHOULD be recognized case-insensitively as natural language reserved words. System instructions for Canon Clerk AI SHOULD highlight and explain the behavioral meanings of these keywords. 

#### B. Section Header Syntax
Best suited for Tier 3 structured canons:
```markdown
## Guidance
Direct the author to `docs/contributing.md#test-plans` and enumerate the missing verification criteria.
```

```markdown
## Supplement
Synthesize a 3-step manual Test Script covering each modified visual state.
```

## 6. File Naming & Numbering Conventions

1. **Descriptive Kebab-Case Slugs (Recommended):**
   * Canons should be named with descriptive, kebab-case slugs that convey their invariant at a glance:
     * `no-new-features-without-documentation.md`
     * `manual-test-plan-required.md`
     * `bounded-context-api-isolation.md`
2. **Sequential Numbering (Optional):**
   * Teams that prefer numeric prefixing (e.g., `canon-0001-falsifiable-canons.md`) may use it. Sequential numbering is strictly an organizational preference and is **never required by the engine**.
3. **No File Collisions:**
   * Because each canon maps to a single file at a specific path, strict collisions are impossible.
   * UIs describing canons SHOULD make each canon's repository relative file path discoverable for disambiguation between similarly named canons files.

## 7. Evaluation Cascade & Verdict Matrix

Canon Clerk evaluates applicable canons through a three-stage cascade:

```mermaid
flowchart LR
    PR[Pull Request] --> S0[Stage 0: Path Filter\n(Deterministic Globs)]
    S0 -- "Matched Canons\n(0 tokens)" --> S1[Stage 1: Screener\n(Fast LLM)]
    S1 -- "Applicable Canons" --> S2[Stage 2: Deep Auditor\n(Reasoning LLM)]
    S2 --> Verdict[PR Verdict & Annotations]
```

### 7.1 Cascade Stages
1. **Stage 0 (Path Filter - Deterministic):**  
   Evaluates `paths:` globs against the PR's modified file list. If none match, the canon is discarded with zero token cost and zero latency.
2. **Stage 1 (Screener - Fast LLM or System One Model):**  
   Evaluates PR title, description, and diff statistics (file list, additions/deletions) against candidate canons to determine potential applicability.
3. **Stage 2 (Deep Auditor - Reasoning LLM):**  
   Evaluates the actual git diff and scoped context against the screened-in canons, returning a structured verdict, possibly with Guidance or Supplement.

### 7.2 Verdict Matrix

| Engine Verdict | GitHub Check Run Conclusion | Blocks Merge? | Scope & Conditions |
| :--- | :--- | :--- | :--- |
| **`pass`** | `success` 🟢 | No | Canon applies and the PR fully conforms to the invariant. |
| **`fail`** | `failure` 🔴 | **Yes** | PR violates the invariant. Includes cases where a `Guidance` directive was provided, or a `Supplement` attempt was infeasible. |
| **`action_required`** | `action_required` 🟡 | **Yes** | PR violates process/metadata invariants (e.g., missing PR description section, invalid PR title). Includes human `Guidance`. |
| **`warn`** | `neutral` ⚪ | No | PR is compliant or advisory. Applied when the Clerk successfully synthesizes a `Supplement` (curing the defect). |
| **`skipped`** | `skipped` ⚪ | No | Canon was flagged as potentially applicable in Stage 1, but determined to be inapplicable upon inspecting full diff context in Stage 2. |
